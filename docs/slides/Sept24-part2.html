9 · Persistent instructions and memory

Instructions that are there before you type: somebody else’s first, then yours.

Somebody already wrote instructions

Every conversation you had this morning already contained a block of text you did not write and never saw.

The system prompt. It sits ahead of your first message and is sent again on every turn, telling the model what it is, what it may do, and how to answer.

What is in one

Identity what it is, who made it, what today’s date is
Format when to use markdown, how long an answer should run, when to use a list
Tools when to search the web, when to write code, when to make an artifact
Refusals what it declines, and how
Character what to do when it is uncertain, how much to hedge

Thousands of words, revised often, and paid for on every turn.

Read the real one

Anthropic publishes the system prompts for the Claude apps, dated and by model:

platform.claude.com/docs/en/release-notes/system-prompts

Worth reading. Behavior you took for the model is often an instruction on that page.

It does not come with the API

Call the Messages endpoint the way you did this morning and none of that is there.

The system field is empty unless you fill it. Same weights, same training, no instructions — which is why a question can get one answer in the chat window and a different one from a script.

The scaffolding is in the app, not in the weights.

Who writes it, where

Where you are Who wrote the system prompt
claude.ai, Claude Desktop Anthropic, and published
Claude Code Anthropic, not published
OpenRouter, or any raw API call you, or nobody
An agent you build you, entirely

Further down the list, more of the behavior is yours to specify, and absent if you do not. Sunday you write one.

The repeated instruction

This morning you typed the same four things into every prompt: describe the data first, show the code, report row counts, reconcile a second way.

Each of those is a standing instruction about how you want work done. Typing them into each prompt makes them optional, and eventually one gets left out.

Everything arrives as one block of text

Each turn, the harness assembles the request from parts you can control:

Part Set by When it is sent
System prompt the tool every turn
Tool definitions the tool and your config every turn
CLAUDE.md you every turn
Skill descriptions you every turn, one line each
A skill’s body you only when that skill is used
The conversation you and the tools growing, every turn

The cost of always

A file read on every turn is paid for on every turn — in money, in latency, and in the model’s attention.

CLAUDE.md

Short and always present. Standing rules that apply to everything you do in that folder.

A skill

One line always present — its description. The body arrives only when the description matches what you asked for.

A CLAUDE.md that runs to three thousand words is paid for on every turn, including the turns none of it applies to.

What belongs in each

Standing rules

  • How you want numbers handled
  • What the folders hold
  • Conventions everything here follows
  • Anything you have corrected twice

Not standing rules

  • Steps for one particular task
  • Anything longer than a page
  • Background that can be looked up
  • A tool you use once a month

Write your standing rules

Exercise

  1. Create ~/CLAUDE.md in your container.
  2. Write the four rules from this morning in your own words, and two more of your own.
  3. Start a new conversation and give it a task that would break one of the rules.
  4. Change a rule and watch the behavior change.

Ask it to name the rules it is following. If it cannot, the file is not being read.

Skills

A skill is a folder

country-report/
  SKILL.md          the instructions
  references/       longer material, read only when needed
  scripts/          code the skill runs rather than regenerates

SKILL.md opens with two lines of metadata and then plain prose:

---
name: country-report
description: Build the monthly revenue-by-country report from the
  order spreadsheets. Use when asked for the country report, the
  monthly revenue rollup, or revenue by market.
---

The description is the trigger

Does not fire

“Helps with reporting.”

Fires

“Build the monthly revenue-by-country report from the order spreadsheets. Use when asked for the country report, the monthly revenue rollup, or revenue by market.”

The description is the only part of a skill always in front of the model, and it decides whether the rest is ever read. Write the words the person asking would use.

What goes in the body

  1. What the task produces, stated first.
  2. Where the inputs are, by path.
  3. The steps in order, including the checks.
  4. What to do when something is missing.
  5. What the output looks like when it is right.

Prose, not pseudocode. The reader is a model that already knows Python and does not know your files.

Scripts beat instructions

Instructions

The code is written fresh each time. Same intent, a different implementation, different bugs.

A script

The code is written once and tested. The skill says when to run it and what the arguments mean.

Three ways to invoke

How When
Slash command /country-report you know exactly what you want
By name “use the country report skill” you are half sure
Automatically “build me the March rollup” the description matched

The third only happens if the description was written for it.

Already in your container

Skill What it does
xlsx builds and edits Excel workbooks, with formulas and charts
docx the same for Word, including templates
pptx the same for PowerPoint, including an existing deck
finance-data pulls prices, fundamentals and macro series
web-app scaffolds an app you can serve on port 8000
skill-creator writes and tests a new skill

Open one. It is the same kind of file you are about to write.

Write a skill

Exercise

  1. Pick something you do at work more than once a month, with inputs and a shape. If nothing comes in two minutes, use Thursday’s revenue-by-country report.
  2. Run /skill-creator and work through it, answering in your own vocabulary.
  3. Put a real input file in the container and run the skill on it.
  4. In a fresh conversation, ask for the task in the words a colleague would use.
  5. Fix the description until it fires.

A skill that fires only when you name it needs a better description.

10 · Connectors and plugins

The problem a standard solves

Every tool wants to reach every data source. Without a standard, that is one integration per pair.

N × M integrations without a protocol

N + M with one

A server written for nothing in particular is reachable from every client that speaks the protocol.

What a connector sends

  1. The client connects to the server and asks what it offers.
  2. The server returns a list of tools: each with a name, a description in English, and the parameters it takes.
  3. That list goes into the model’s context alongside its built-in tools.
  4. The model asks for one by name. The client calls the server and puts the result back in the conversation.

The model does not know a connector from a built-in tool. Both are entries in the same list.

A tool definition

{
  "name": "run_sql",
  "description": "Run a read-only SQL query against the Northwind
                  database and return the rows. SELECT only.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "A SELECT statement"}
    },
    "required": ["query"]
  }
}

The description is what the model reads to decide whether to use it.

Where the call is made from

In Claude Cowork, and in most setups a firm will hand you, the machine the agent’s shell runs on has no route to the internet. The connector works anyway.

At the shell

curl https://api.stlouisfed.org/...

Refused. Everything leaving that machine passes a proxy that allows a short list of addresses, and that is not one of them.

Through the connector

fred_get_observations("UNRATE")

Rows come back. Same machine, same second, same model.

Because your machine never places the call. The client end sits outside it, calls FRED itself, and hands the rows back into the conversation. Your key goes with it and is never on the machine to steal.

A narrower door, not a hole

Open the network instead

Allow the machine to reach stlouisfed.org and it can send anything to any address there, in any form it likes.

Leave it shut, add a connector

It can call run_sql with a SELECT. That is the entire new capability.

The connector is the smaller of the two. That is why the network stays off and the connector goes on.

It costs something. The connector reaches out from outside the sandbox holding your credentials, so a sentence in a file it reads can ask for that call. Cutting the machine off from the network did not cut off the connector. Sunday morning.

Servers you can connect today

Server Address Sign-in

The Northwind server

Exercise

  1. Connect the Northwind server and ask what tools it offers. Read the descriptions.
  2. Ask which countries generated the most revenue, and have it show you the SQL it ran.
  3. Put that beside the number you computed from the spreadsheets on Thursday morning.
  4. Explain any difference. One of the two is answering a slightly different question.
  5. Try to make it change something in the database.

The two numbers usually differ. Freight, discounts, cancelled orders, and shipped versus ordered date are the usual causes.

What discovery looks like

The EIA server does not hand the model a list of datasets. It hands it a way to find one.

eia_search_routes fuzzy search — “electricity prices by state”
eia_browse_routes walk the taxonomy; fourteen categories at the root
eia_describe_route what filters exist, what columns, what units
eia_query_route the rows, with the filters applied
eia_dataframe_describe what has been pulled so far, and its schema
eia_dataframe_query SQL across those, joins included

Six tools rather than one per dataset. The model reads the descriptions and works out the order, which takes about four turns.

The EIA server

Exercise

  1. Connect the EIA server and ask what tools it offers. Read them before using any.
  2. Have it browse the taxonomy from the root and pick the category closest to your industry.
  3. Ask a question you do not already know the answer to. Make it name the route it used, the filters it applied, and the units.
  4. Ask a second question that needs two of those series in one answer.
  5. Ask for something the server has no tool for, and watch what it does instead.

Energy arrives in thousand megawatthours, million cubic feet, and thousand barrels a day. A right number with the wrong unit is wrong by a factor of a thousand, and nothing in the reply will say so.

Where the limit lives

Read-only, enforced four ways

Where What refuses
The database a role without write permission
The application a whitelist of allowed operations
The connector run_sql rejecting anything that is not a SELECT
The tool list no write tool exists to call

The model is not consulted at any of them.

Instructions are not a limit

A rule in a prompt

“Never modify the database.”

Text in a conversation, competing with other text in the same conversation.

A tool that does not exist

There is nothing to call.

No wording reaches it, because nothing is being persuaded.

Mail and calendar

The same shape applied to an inbox: an agent that reads everything and sends nothing.

It reads

Threads, calendar entries, attachments. Enough to tell you what is waiting and what it is about.

It drafts

Replies, parked where you can read them.

It does not send

No send tool, no delete tool. Sending stays a thing you do.

Two things at once

An agent reading your mail is holding two things at once: your private correspondence, and text written by people outside your organization.

Give it an outbound channel and text written by outsiders can direct what leaves. Sunday, in detail.

Installing plugins

What you install

A plugin is a folder somebody else published. Installing it adds their work to your Claude in one step.

What it can carry

Skills, slash commands, subagents, hooks, and MCP servers.

What you get

Every file and script in it, without being told which ones to copy where.

Two commands

/plugin marketplace add kerryback/skills
/plugin install finance-data@kerryback

The first points Claude at a public repository holding an index of plugins. The second installs one of them. /plugin on its own lists what you have.

A marketplace you can use today

kerryback/skills holds fifteen. Seven of them:

finance-data prices, fundamentals, SEC filings and macro series, as CSV
elegant-pdf branded flyers, programs and reports as print-quality PDF
critique parallel reviewers on work Claude produced, and what to do
human-write prose that does not read as machine-generated
shoji2 Quarto slide decks in the theme these slides use
voiceover a narrated MP4 and transcript from a deck
smithers a read-only desk over your mail and calendar

Read it before you install

An installed plugin runs with your permissions, on your machine, against your files.

  1. Open the repository and read the SKILL.md of anything you are about to install.
  2. Check what it runs: a script, a command, an MCP server reaching outside.
  3. Install into a container first when you are not sure.

Same question as Sunday morning’s, asked earlier: what can it reach, and what can leave.

Install and try

Demonstration · 10 minutes

  1. Add the kerryback/skills marketplace and list what is in it.
  2. Install one and run it.
  3. Open its SKILL.md and read how it does what it does.

Install what you want tonight. The marketplace stays in your container all week.

Four rungs

Where it lives Who has it
A prompt in your head you, when you remember
CLAUDE.md one folder anyone working in that folder
A skill a file you, everywhere, when it matches
A plugin a repository someone published anyone who installs it

The same instruction each time, moved somewhere that outlasts the conversation.

11 · Agent harnesses

Claude Code is one answer to a design problem. There are others, increasingly not from the model’s maker.

Same model, different program

The model is a string in a config file. Everything you experience as “the tool” is the program wrapped around it: what it sends each turn, which tools it offers, how it asks permission, and where it runs.

The harness is the other five

You pick the model. Everything else on that list is supplied by the program around it.

Buying a harness — Claude Code, or one of the open ones — is buying somebody’s answers to those questions. The answers differ, and the differences show up in the output.

What differs

The question it answers
Model coupling one vendor’s models, or any provider you can point it at
Context what gets sent each turn, and what happens when the window fills
Tool surface four tools, or forty
Permissions how it stops — approval rules, an OS sandbox, or a container
Extension plugins, MCP servers, skills, instruction files
Where it lives a terminal, an editor, a web page, or a library you import

Every one of these is a design choice somebody made and wrote down. None of them is the model.

The open field

Claude Code Anthropic models only the reference implementation
Codex OpenAI models only Rust; OS-level sandbox by default
OpenCode 75+ providers the mature open alternative; per-agent permissions
DeepSeek Harness any provider everything is a plugin, including the loop
Pi any provider four tools and a very short prompt
Goose · OpenHands any provider neutral governance; container-first
Qwen Code Alibaba’s models a vendor CLI on the same pattern

Everything but Claude Code is open source, MIT or Apache — you can read the loop. Two of those still only talk to their maker’s models.

Thick or thin

Claude Code

Forty-plus tools. A layered system prompt with a cached boundary. Four fallback strategies when the context fills. Subagents that fork and run in the background.

The harness does a great deal on your behalf.

Pi

Four tools — read, write, edit, run a command. A system prompt under a thousand tokens. No subagents, no plan mode, no MCP.

Anything else, the agent writes for itself as an extension.

Databricks benchmarked both and found the thin one matched or beat the thick one at a fraction of the cost, because it sent roughly three times less context per turn.

The permission model

Harness How it stops you
Claude Code rules you configure, checked before each call
Codex the operating system — Seatbelt on macOS, Landlock on Linux
OpenHands a Docker container the agent cannot leave
Cline a human clicking approve, every time
OpenCode per-agent tool permissions, granted once and remembered

The distinction from this morning, in a different form: a mode that asks you, versus a boundary that makes the call impossible. Two of these five are the second kind.

Benchmarks and harnesses

A benchmark number is a model and a harness together. Change the harness and the number moves.

  1. The same model scores differently under two harnesses on the same benchmark.
  2. Papers report the model and omit the harness.
  3. Removing most of an agent’s tools has been shown to raise its score, not lower it.
  4. So a leaderboard ranks model-and-harness pairs, not models.

When somebody says a model can or cannot do something, ask which harness it was running in.
